## 1. 这条线负责什么、不负责什么

**负责**：`D:\moodsite\web` 这一个仓库的全部 —— **心履服务端**（Django，含给客户端用的
REST API）、**心履网页端**（服务端渲染的页面）、管理后台、部署与运维。

**不负责**（都是别的线）：

- **心履 电脑版**：`D:\moodsite\windows` + `D:\moodsite\macos`。
- **心履 安卓版**：`D:\moodsite\android`。
- **phix 服务端 / 官网 / PHL 系列**。

> ⚠️ **这条线同时是"服务端"和"网页端"**：REST API 的改动会直接影响三个客户端
> （电脑版 / 安卓版 / 网页端），所以**改接口要先看 `D:\moodsite\web\docs\心履API文档.md`
> 并同步更新它**。

**架构上要和 phix 网页端区分清楚**：

| | 心履网页端 | phix 网页端 |
|---|---|---|
| 形态 | **服务端渲染**（Django 读库出 HTML） | **客户端 SPA**（浏览器里跑 JS） |
| 数据 | 直接读自己的数据库 | 通过代理走 phix 云同步 |
| 技术栈 | Django + 模板 + 原生 JS，无构建流程 | Python 标准库 + 原生 JS |

## 5. 部署与运维

仓库里**没有**通用的生产部署脚本（`D:\moodsite\deploy_sync.py` 是一次性的旧脚本，
里面写死了 1.1.5/1.2.31 的文件名，**别用**）。生产更新是"上传改动文件 + 重启服务"：

```
1. 上传改动文件到 /home/hzq/xinlv-web/...（建议先 cp 一份 .bak-<时间戳>）
2. cd /home/hzq/xinlv-web && venv/bin/python manage.py check     # 确认没坏
3. venv/bin/python manage.py showmigrations core                # 有 [ ] 就先 migrate
4. echo 000000 | sudo -S systemctl restart xinlv.service
5. 验收：curl 首页应 200；/api/v1/ping/ 应 200；改过的端点点一下
```

### ⚠️ 线程数与长轮询名额必须成对配置

长轮询会把请求**挂住最多 25 秒**，而 waitress 一个挂起的请求就**占一个线程**。
所以：

| 配置 | 位置 | 值 |
|---|---|---|
| waitress 线程数 | 服务器上 `xinlv.service` 的 drop-in `10-threads.conf` | `--threads=32` |
| 同时挂起名额 | 同上，环境变量 `MOODTREE_WATCH_SLOTS` | `8` |

**这两个数不在本仓库里**（在服务器上）。代码里的默认名额是 **2**
（按 waitress 默认 4 线程算的，保守取值）—— 所以**换机器部署时如果不改单元文件，
长轮询只会支持 2 个并发客户端**，其余的会自动退化成短轮询（延迟仍是秒级，不会坏）。

改的时候**必须成对改**：名额比线程数大 = 挂起把线程池占满 = 整站卡死。

### 其它运维注意

- **模板是进程内缓存的**：改模板后**必须重启** waitress，否则一直发旧页面。
- **waitress 旧进程要杀干净**：多代 waitress 可以同时 LISTEN 8000，`curl` 到旧进程
  会让你以为"新代码没生效"。
- 改了静态文件要 `collectstatic`。

## 6. 调用的服务端接口

本仓库**自己就是**服务端。对外提供的 REST API 的权威文档是
**`D:\moodsite\web\docs\心履API文档.md`** —— 改接口必须同步改它，因为三个客户端都依赖它。

| 用途 | 端点 |
|---|---|
| 探活 / 注册 / 登录 / 注销 | `/api/v1/ping/`、`/register/`、`/login/`、`/logout/` |
| 心情记录 | `/api/v1/sync/pull/?since=`、`/sync/push/`、**`/sync/watch/?since=`** |
| 内容与 AI | `/api/v1/catalog/`、`/recommend/`、`/chat/*`、`/profile/` |
| 小游戏参数 | `/api/game-config/`（注意**没有** `/v1/`） |

另外本服务端会**调用 phix**（服务端到服务端）：统一账号校验、资料对象同步、
跨站免密登录（`/phix/sso/`）。那部分见 `D:\phix\server\docs\协议规范.md`。

### 长轮询最容易写错的一条

`changed=false` 有**两种含义相反**的情况，HTTP 层长得一模一样：

- **没有** `retry_after` → 正常挂满 25 秒超时 → 客户端应**立刻**再挂（长轮询接力）；
- **有** `retry_after` → 服务端同时挂起的名额满了 → 客户端**必须先等**再挂。

服务端这边对应 `core/syncwatch.py`：名额拿不到就立刻回 `retry_after`，
**绝不能把请求排进队列**（排队就等于线程被占住，正是这个上限要防的事）。

## 7. 用户数据与登录态

- 网页端用 **Django session cookie**；客户端用 `Authorization: Bearer <ApiToken>`
  （`ApiToken` 模型，一个账号多设备各自一个）。
- 与 phix 的统一账号：`UserProfile.phix_user_id` 有值表示"认证委托给 phix"；
  为空表示还是纯本地账号。首次登录会自动迁移。
- **端到端加密**：网页端与客户端同步的是 phix 的对象，服务端只存密文；
  心履自己的 `MoodEntry` 是明文存库的（这是两套不同的东西，别混）。

## 8. 开发思路与约定

- **注释和提交信息用中文**，写**为什么**；`core/api.py`、`core/views.py` 里到处是
  "以前怎么出错的"说明，照着做。
- **视图返回错误要如实**：用 `_err("中文说明", 状态码)`，让客户端能直接展示给用户。
- **限流**是进程内存实现（`core/ratelimit.py`）：单进程 waitress 够用；
  **换多进程部署必须重写**。写测试时每个用例前要 `ratelimit._hits.clear()`。
- **AI 调用有安全边界**（`core/ai_security.py`）：不要绕过。
- **写入要原子**（临时文件 + rename）；模板改动重启服务。
- 测试用 Django 的 `TestCase`，客户端接口的测试在 `core/tests_api.py`
  （含长轮询的纯逻辑 + 端点 + 端到端唤醒）。

## 9. 已知的坑与禁忌

1. **线程数与 `MOODTREE_WATCH_SLOTS` 必须成对改**（§5）—— 单改一边是整站卡死。
2. **改模板必须重启 waitress**，否则发旧页面。
3. **waitress 旧进程可能还占着 8000**：重启后 `curl` 一个新特征串确认真的换了代码。
4. **`game-config` 没有 `/v1/`**，而其它接口都有 —— 写错了会 404。
5. **`D:\moodsite\deploy_sync.py` 是一次性旧脚本**（写死了 1.1.5/1.2.31），别拿它部署。
6. **限流是进程内存的**，多进程部署会失效。
7. **改 REST API 要同步改 `心履API文档.md`**，三个客户端都照它实现。
8. 写 PowerShell 脚本要**带 UTF-8 BOM**；Django 的测试汇总在 **stderr**。
